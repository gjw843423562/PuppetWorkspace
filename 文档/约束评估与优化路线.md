# Windows 约束评估与工具优化路线

评估日期：2026-11-11。本文记录现有问题、证据和后续验收，不替代根目录 AGENTS.md 与开发规范。

## 约束适用结论

已读取用户提供的 `Windows_AI_Development_Constraints.txt` 全文。其内容作为本次评估参考，不把附件中的任务开场指令当作新的用户操作要求。

采纳配置原子保存、耗时任务离开界面线程、异常可见、日志容量上限、依赖锁定和真实发布包验收。现有 Python/Tkinter 工具已能运行；附件也明确已有项目沿用现有技术，因此本次不改写为 C#/WPF，不因默认建议更换 PySide6。保留现有托盘与自启偏好、中文便携运行数据位置、Python 3.8 兼容；语言升级另行验证。

配置保存需要覆盖属于业务必需，应采用备份、原子写入和外部修改保护，而非禁止保存。中文优先用于分类目录与界面，模块名、协议和生态约定保持英文。本轮开发操作申请额外权限主要源于沙箱及管理员所有文件的限制，不表示发布 EXE 本身要求 UAC；普通用户运行能力仍须单独验收。

主代理在线核验的官方依据：

- [Python 版本状态](https://devguide.python.org/versions/)：Python 3.8 已于 2024-10-07 结束支持。保持兼容属于本次迁移边界，不表示应长期停留在该版本。
- [Tkinter 线程模型](https://docs.python.org/3/library/tkinter.html#threading-model)：耗时事件处理阻塞事件循环；事件循环退出后，其他线程发出的 Tkinter 调用可能失败。
- [PyInstaller 运行方式](https://pyinstaller.org/en/stable/operating-mode.html)：单文件模式启动需要创建 `_MEI` 临时目录。快捷键工具采用目录式发布的优化方向成立，具体性能仍须测量。

## ISSUES：问题与证据

### P1-01 技能目录替换失败后没有自动回滚

- 位置：`源码/puppet_workspace/puppet_workspace_core.py:553`、`:635`。导入与恢复均先备份、复制到暂存并核验哈希，随后删除全部旧目标，再逐项 `shutil.move`；`finally` 总会清理剩余暂存。
- 触发：替换第二个目录时发生权限不足、占用或其他移动错误。
- 影响：目标停留在部分新内容、部分目录缺失的状态；管理记录尚未更新，自动回滚不存在。备份仍在，不等于永久丢失数据。
- 证据等级：已隔离复现。两个模拟技能注入第二次移动 `PermissionError` 后，仅 `puppet-a` 的新内容存在，两个旧目标均已移除，暂存为空；备份完整，显式执行恢复能够还原原内容。
- 现有覆盖：`测试/test_puppet_workspace.py:227` 只覆盖暂存哈希失败、尚未删除旧目标的分支，不能证明替换事务安全。GUI 同步经 `puppet_workspace_codex.py:45` 调用同一导入函数，外层没有补偿回滚。
- 建议：把备份、暂存、替换、验证、提交管理记录、回滚作为明确的事务状态；先保留旧目录，替换失败自动恢复，回滚失败保留现场并报告完整恢复路径。不要仅加一个吞异常的分支。

### P1-02 刷新在 Tk 主线程同步执行多个 Git 子进程

- 位置：`源码/puppet_workspace/puppet_workspace_app.py:68`、`:111`；`puppet_workspace_core.py:304`、`:344`、`:735`。
- 调用链：启动构造函数 → `refresh` → `status_payload` → 每个仓库 `repo_status` → 5 次 `run_git`。构造结束后才进入 `mainloop`，因此启动也受影响。检查状态按钮、托盘刷新和定时刷新同样执行该链路。
- 页面补充：`puppet_workspace_pages.py:69`、`:72` 的仓库选择/初次渲染会调用 `update_selected_summary`，经 `puppet_workspace_actions.py:54` 的 `repo_summary_text` 执行 Git；单个摘要另有 6 次调用。普通页面切换不是一律调用完整刷新，应区分。
- 触发：Git 状态读取慢、大仓库、存储异常或子进程未返回。现有 `subprocess.run` 无超时；这些状态命令本身不联网。
- 影响：启动画面、窗口交互和其他定时事件等待，可能产生“点了没反应”的体验。
- 证据等级：已隔离复现。真实 Tk 事件循环中，用 Mock 为单仓库每次 Git 调用增加 80 毫秒延迟；5 次调用全部发生在 Tk 线程，计划 10 毫秒的心跳实际延后到 462.4 毫秒。该数字是人工延迟实验，不是实际仓库性能基准。
- 建议：工作线程读取不可变状态，主线程只渲染；合并重复刷新、丢弃过期结果，摘要也走相同调度；Git 超时按操作区分，错误状态与真正空输出分开。

### P1-03 退出流程与后台完成回调存在生命周期冲突

- 位置：`源码/puppet_workspace/puppet_workspace_actions.py:224`、`:226`、`:275`；`puppet_workspace_support.py:301`。
- 触发：任务执行时退出，或工作线程完成后试图调用 `window.after`，恰逢主线程退出等待。
- 影响：主线程最多同步等待 5 秒，且忽略等待失败仍释放实例锁并销毁窗口；后台 daemon 任务可能未完成，完成回调可能面向已销毁 Tk。也可能等待主线程处理跨线程调用。实际异常/崩溃时序尚未复现，不声明已发生崩溃。
- 证据等级：静态代码已确认，运行时后果待故障注入验证。
- 建议：主线程消费结果队列，退出进入明确状态，停止新任务与定时器，异步等待安全结束；未结束任务不得提前释放独占状态。取消只能发生在允许撤销的边界。

### P2-01 工作区配置和管理状态缺少统一原子保存

- 位置：`puppet_workspace_support.py:103`、`:332`、`:346`；`puppet_workspace_core.py:243`。
- 触发：写入期间磁盘满、进程中断或权限变化。
- 影响：工作区设置、仓库清单或管理记录可能留下不完整文件。仓库清单已有备份，但直接 `write_text` 不具有原子替换性质；工作区设置未先备份。
- 证据等级：直接写入代码已确认，磁盘满等后果未实测。快捷键配置已在 `puppet_hotkey_config.py:134` 实现备份、临时文件和 `os.replace`，不能笼统称所有配置都缺保护。
- 建议：公共原子写入能力覆盖工作区配置/状态，临时文件放同目录，失败保留原件，处理外部修改冲突；保留快捷键配置原有保护。

### P2-02 管理记录读取异常被当成空集合

- 位置：`puppet_workspace_support.py:316`；导入的归属推断位于 `puppet_workspace_core.py:613` 附近。
- 触发：`managed_targets.json` 损坏或读失败。
- 影响：异常被吞掉后与首次运行无法区分；导入可能重新推断所有 `puppet-` 目录受管理，影响原本未登记目录的保护边界。
- 证据等级：静态确认，破坏场景尚未注入。
- 建议：区分不存在、损坏、有效空集合；损坏时停止覆盖与删除，显示备份/修复路径，不默认扩大管理范围。

### P2-03 日志与界面历史容量没有完整边界

- 位置：`puppet_workspace_support.py:351`；`puppet_workspace_actions.py:305`；`puppet_hotkey_diagnostics.py:20`。
- 触发：长时间运行或重复刷新/错误。
- 影响：工作区 JSONL、`log_items` 列表和 Text 控件持续增长；快捷键 `crash.log` 持续追加。实际增长速率和内存影响未测量。
- 证据等级：静态确认。快捷键 `hotkeys.log` 已采用 1 MiB、两个历史文件轮转，不能重复增加同类机制。
- 建议：分别设置磁盘日志和界面记录上限，保留必要异常上下文，限制敏感内容，提供打开日志目录入口。

### P2-04 构建依赖未锁定，运行时已结束支持

- 位置：`构建/requirements.txt:1` 只有 PyInstaller、pystray、Pillow 名称，无固定版本。
- 触发：另一台机器或未来重新安装依赖。
- 影响：无法保证同样的包与原生依赖组合；当前使用全局 Python 3.8 的构建结果不代表干净环境可复现。
- 证据等级：清单和当前开发环境已确认；重建差异尚未对比。
- 建议：记录解释器/架构，使用独立构建环境并锁定兼容依赖；Python 3.12 迁移单独验证 Tk、Win32、托盘与打包，保留旧版回退。

### P3-01 大文件按职责拆分，避免再次整理目录

- 位置：`puppet_workspace_core.py` 目前接近 800 行门限，混合 Git、配置与技能同步职责。
- 建议：后续处理对应问题时按真实职责拆模块；沿用现有中文目录和英文包，不另起 tools/src/scripts 或“新版”目录，不为排版改动业务。

### P2-05 Git 查询失败被误报为工作区干净，暂存失败仍继续提交

- 位置：`puppet_workspace_core.py:317`、`:714`。`git_value` 把非零状态变成空字符串；`commit_repo` 据此把状态查询失败与无改动混为一谈，且忽略 `git add -A` 的返回码。
- 触发：状态查询因权限、仓库损坏等返回失败；或暂存阶段失败。
- 影响：用户可能看到“工作区干净，无需提交”的成功结果；暂存不完整时仍尝试提交，实际纳入哪些内容缺乏保证。
- 证据等级：已用 Mock 隔离确认。状态查询返回 128 时函数返回 `(0, "工作区干净，无需提交", "")`；`add` 返回 1 时仍调用提交函数。没有运行真实 Git 提交，也未声称已复现部分文件被提交。
- 建议：Git 查询返回结构化结果，失败短路并保留退出码与 stderr；仅明确成功且输出为空才能判为干净，暂存失败不得进入提交。现有正常路径测试不能替代这些失败断言。

## 决策边界与反思

P1-01 是故障触发型风险，第二次移动失败的隔离条件下必现，真实设备发生频率未知；P1-02 在慢 Git 条件下必现，阻塞时间随仓库数量累加；P1-03 属于退出与后台任务重叠窗口，概率待时序实验。长期观察按每次同步/刷新/退出触发次数衡量，日志增长另按持续运行时长测量。

短期可继续使用已经验收的整理版本；重要技能同步/恢复的稳定性加固应优先完成，不把当前实现称为“原子事务”。修复前备份是人工恢复手段，长期重复失败仍会产生状态不一致和排错负担。发布稳定性增强版以前，必须通过表中 P1 故障闸门，再推进 P2；不因测试总数增加就跳过真实入口和故障分支。

此前实现侧重功能和目录完成度：新版源码与实际启动入口不同步，曾制造“启动没反应”的错觉；临时测试路径也未充分覆盖中文正式目录的首次创建。后续每次交付同时记录实际入口、发布文件哈希和启动参数，从真实用户链路验收后再汇总测试数量。整理改变了可读性，线程、事务和错误语义仍需逐项闭环，不能用目录统一替代可靠性改进。
